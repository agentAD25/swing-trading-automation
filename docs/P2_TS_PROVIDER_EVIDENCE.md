## Q1 — OAuth application type

**PROVIDER CONFIRMED.** A Regular Web Application uses the standard
Authorization Code flow and must send `client_secret`. A Native or Single
Page application can use Authorization Code with PKCE, omit
`client_secret`, and send a Code Verifier.

**OPEN QUESTION.** TradeStation did not choose Regular Web, Native, or
Single Page. Confidential Authorization Code plus PKCE was not confirmed.

**ENGINEERING RECOMMENDATION, not selected.** Native plus Authorization
Code with PKCE would avoid a persistent client secret on an attended,
read-only, no-refresh first probe. It is not selected. The callback form
for that Native client is not established (`Q6`).

## Q2 — SIM-only credential

**PROVIDER CONFIRMED.** A SIM-only API key is not available. The same key
is used for both environments. The request base URL is what differs.

`PROVIDER_ENFORCED_SIM_ONLY_API_KEY = NOT_AVAILABLE`.

Any future credential is
`POTENTIALLY_LIVE_CAPABLE_PROVIDER_CREDENTIAL`. This does not weaken LIVE
denial. Independent application, transport, configuration, and test
controls must keep the LIVE host unreachable. See the control list in
`docs/P2_PRE_CREDENTIAL_DECISION.md`.

## Q3 — Minimum scopes

**PROVIDER CONFIRMED, partial.** "Once a key has been generated and
provided, this could be configured."

`MINIMUM_SCOPE_CONFIGURATION = PROVIDER_SUPPORTED`.

**OPEN QUESTION.** The answer does not establish that every authorization
request can ask for an arbitrary strict subset, how returned `scope`
behaves, how default-scope configuration works, capitalization or
tokenization, or that `Trade` can be omitted dynamically without key
configuration. The published three-way default-scope conflict (U-02)
remains a documentation conflict.

**OPERATOR DECISION, desired and not yet observed.** The initial
configuration to request remains `openid` and `ReadAccount` only. `Trade`,
`MarketData`, `Matrix`, `OptionSpreads`, and `offline_access` stay
omitted unless a later written requirement proves one is technically
necessary. A future probe must compare granted scope with requested scope
before any brokerage call. Unexpected economic scope, including `Trade`,
is `UNEXPECTED_SCOPE_GRANTED`: stop, and do not list accounts.

limited to a maximum lifetime of 20 minutes before re-authorization.

`OFFLINE_ACCESS_OPTIONAL_FOR_ATTENDED_PROBE = CONFIRMED`

`FIRST_PROBE_OFFLINE_ACCESS = OMIT`

`FIRST_PROBE_REFRESH_TOKEN_REQUIRED = NO`

This supersedes U-17 for the attended no-refresh probe: Client Experience

## Q5 — Refresh-token behavior

**PROVIDER CONFIRMED for the stated default.** Default personal-use API
keys use non-rotating, non-expiring, long-lived refresh tokens. Access
tokens obtained from a refresh token last at most 20 minutes.

`DEFAULT_PERSONAL_KEY_REFRESH_TOKEN_ROTATION = NON_ROTATING`

`DEFAULT_PERSONAL_KEY_REFRESH_TOKEN_EXPIRY = NON_EXPIRING / LONG_LIVED`

`REFRESHED_ACCESS_TOKEN_MAX_LIFETIME = 20 MINUTES`

**OPEN QUESTION.** Concurrent refresh, revocation, non-default key
configurations, and differences by application type were not answered.
The published 30-versus-40-minute conflict remains open for an optional
rotating configuration. It does not describe this default.

A long-lived refresh token is a high-value secret. It is out of scope for
the first probe because `offline_access` is omitted. Before any unattended
phase, custody, revocation, refresh concurrency, replacement if
configuration changes, compromise response, and TokenStore behavior must
be certified. Persistent TokenStore use is not part of the first probe.

## Q7 — Account and SIM entitlement

**PROVIDER CONFIRMED.** API key access is limited to accounts accessible
under that login. The key is linked to that login. Other clients' accounts
are not accessible without prior authorization. No additional entitlement
is required to view the login's own accounts or data subscriptions.

`ACCOUNT_ACCESS_BOUNDARY = AUTHENTICATED LOGIN'S ACCESSIBLE ACCOUNTS`

`ADDITIONAL_READ_ENTITLEMENT_FOR_OWN_ACCOUNTS = NOT_REQUIRED`

**OPEN QUESTION.** Which SIM accounts exist, and whether the Operator
accepts that inventory, are not answered. Raw account identifiers stay
out of Git, docs, pull requests, chat, and ordinary logs.

## Q8 — Rate limiting

**PROVIDER CONFIRMED.** Rate limits are enforced per login used to access
a key. Additional logins can be provisioned and then share the same key,
secret, and refresh token while keeping separate rate and streaming
limits.

`RATE_LIMIT_IDENTITY = LOGIN`

**OPEN QUESTION.** Numeric quotas, header presence, and aggregation across
processes or tokens under one login were not answered.

**OPERATOR DECISION.** Do not provision additional logins. The initial
system is one login. On HTTP 429, stop. No blind retry on the first
probe. If `X-RateLimit-*` headers are present, keep sanitized limit
metadata only. Absence of those headers is not itself a probe failure
unless a later document requires them.
